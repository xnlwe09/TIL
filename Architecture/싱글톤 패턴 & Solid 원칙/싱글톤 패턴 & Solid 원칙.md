# 싱글톤 패턴 & Solid 원칙

## Singleton Pattern이란?

특정 용도로 객체를 하나만 생성하여 공용으로 사용하고 싶을 때 사용하는 디자인 유형

앱 전체에서 인스턴스를 단 하나만 생성해서 공유

어떤 클래스에 대한 Instance는 최초 생성될 때 딱 한번만 생성해서 전역에 두고,

그 이후로는 이 Instance만 접근 가능하게!!

## 싱글톤 패턴을 왜 사용할까?

앱이나 프로그램에서 공유된 데이터나 공통 기능이 필요할 때 사용

여러 인스턴스가 생기면 데이터가 일관되지 않을 수 있기 때문에 하나의 인스턴스만 유지하게 해줌

## 싱글톤 패턴의 장단점

### 장점

- 객체가 하나만 존재하기 때문에 메모리 낭비를 줄일 수 있음
- 어디서든 같은 인스턴스를 사용할 수 있기 때문에 데이터 일관성이 유지됨
- 전역에서 접근이 쉬움

### 단점

- 전역 접근이 쉬움 → 객체가 여러 곳에서 사용하기 때문에 코드가 복잡해질 수 있음
- 인스턴스가 앱 전체에서 하나만 유지되기 때문에 테스트 시 상태가 공유되어 테스트 간 독립성이 깨질 수 있음
    
    ‼️ 의존성 주입(DI)을 사용하면 객체의 의존성을 줄이고 테스트가 용이해진다

## Solid 원칙이란?

객체 설계에 필요한 5가지 원칙으로써 유지보수가 쉽고, 유연하고, 확장이 쉬운 소프트웨어를 만들기 위한 수단

<aside>

### **S** (Single Responsibility Principle) : **단일 책임 원칙**

모든 클래스는 하나의 책임만 가지며, 클래스는 그 책임을 완전히 캡슐화해야 한다.

</aside>

<aside>

### **O** (Open / Close Principle) : **개방/폐쇄 원칙**

소프트웨어 개체(클래스, 모듈, 함수 등)는 확장에 대해 열려 있어야하고, 수정에 대해서는 닫혀 있어야한다.

기능 케이스를 추가할 때도 기존 코드를 변경하지 않고 확장해야함

</aside>

<aside>

### **L** (Liscov Substitution Principle) : **리스코브 치환 원칙**

프로그램의 객체는 프로그램의 정확성을 깨뜨리지 않으면서 하위 타입의 인스턴스로 바꿀 수 있어야한다.

- 서브타입은 상속받은 기본타입으로 대체 가능해야한다.
- 자식 클래스는 부모 클래스 동작(의미)을 바꾸지 않는다.
- 상속 했을 때 서브클래스는 자신의 슈퍼클래스 대신 사용돼도 같은 동작을 해야한다.
</aside>

<aside>

### **I** (Interface Segregation Principle) : **인터페이스 분리 원칙**

클라이언트가 자신이 이용하지 않는 메서드에 의존하지 않아야 한다.

- 클래스 내에서 사용하지 않는 인터페이스는 구현하지 않아야한다.
- ISP를 통해 시스템의 내부 의존성을 약화시켜 리팩토링, 수정, 재배포를 쉽게 할 수 있다.
</aside>

<aside>

### **D** (Denpendency Inversion Principle) : **의존성 역전 원칙**

상위 모듈이 하위 모듈에 의존하면 안된다.

- 상위 모듈과 하위 모듈 모두 추상화에 의존해야한다.
- 추상화는 세부 사항에 의존해서는 안된다.
</aside>

## 왜 사용할까?

- 쉽게 변경이 가능한 유연한 코드를 가짐 → 재사용 및 유지관리 가능
- 확장성이 뛰어나며 새로운 기능을 추가하기 용이함
- 응집력(본인 역할)이 높고 결합도(다른 객체에 대한 의존도)가 낮은 소프트웨어를 만들 수 있음
